# In-memory receipt registration

`RegisterInventoryReceipt` accepts an already confirmed document with one complete,
homogeneous, serialized line. It returns a `RegisteredReceipt` containing the
immutable `ReceiptDocument` and its individual `AssetUnit` objects.

The domain uses only Python's standard library. The service depends on repository
and Unit of Work protocols; the in-memory adapter implements those boundaries.
No Flask application, database, migrations, or financial posting is involved.

Run this synthetic example from the repository with `uv run python`:

```python
from datetime import date
from decimal import Decimal

from maas_ua.adapters.memory import FakeStore, FakeUnitOfWork
from maas_ua.domain.receipts import (
    Money,
    Nomenclature,
    Quantity,
    SerialNumber,
    TrackingPolicy,
)
from maas_ua.service_layer.receipts import (
    RegisterInventoryReceipt,
    register_inventory_receipt,
)

store = FakeStore()
command = RegisterInventoryReceipt(
    document_number="EXAMPLE-125",
    document_date=date(2026, 1, 15),
    effective_date=date(2026, 1, 15),
    source="EXAMPLE-SOURCE",
    nomenclature=Nomenclature("EXAMPLE-FPV", TrackingPolicy.SERIALIZED),
    quantity=Quantity(27, "pcs"),
    unit_price=Money(Decimal("14500.00"), "UAH"),
    line_total=Money(Decimal("391500.00"), "UAH"),
    serial_numbers=tuple(
        SerialNumber("EXAMPLE-ISSUER", f"EXAMPLE-FPV-{i:04}") for i in range(1, 28)
    ),
)
result = register_inventory_receipt(command, FakeUnitOfWork(store))
assert len(store.asset_units) == 27
assert result.receipt.lines[0].total.amount == Decimal("391500.00")

# A new UoW over the same store can retrieve committed records.
with FakeUnitOfWork(store) as reader:
    unit = reader.asset_units.get(result.units[0].id)
    assert unit.receipt_line_id == result.receipt.lines[0].id
```

All validation and existing-serial checks complete before repository additions.
The handler commits once after adding the receipt and every unit. Repository
changes remain private until commit; leaving a UoW without committing discards
them. Failed writes leave earlier committed registrations intact. Share a
`FakeStore` between commands to retain data; it disappears when the process ends.
The store exposes read-only committed mappings. A stale transaction is rejected
rather than overwriting a newer commit. This adapter does not provide thread-safe
or cross-process database concurrency guarantees.

The choices below describe Milestone 1. Serial comparison, monetary representation,
and the absence of document-number uniqueness were confirmed for Milestone 2 on
2026-10-30; see [the domain decisions](../architecture/domain-model.md#17-confirmed-milestone-2-receipt-persistence-decisions)
and [PostgreSQL setup](postgresql-receipts.md). Other accounting policies remain open.

- Serial uniqueness uses an explicit caller-supplied namespace and exact,
  case-sensitive text. Blank values and outer whitespace are rejected, without
  normalization. No serial allocation or authorization workflow is implemented.
- Monetary amounts are finite, nonnegative `Decimal` values with an explicit
  currency label. Zero is representable. Multiplication is exact, with no
  currency quantization or rounding. The supplied line total and currency must
  match quantity times unit price.
- Receipt source belongs to the document; optional analytics are captured as
  immutable name/value pairs on the line, without an account-code catalog.
- This operation accepts complete, confirmed input only. It does not implement
  approval, drafts, financial posting, corrections, or document-number uniqueness.
- Document date and effective date are supplied separately; creation time is an
  aware UTC timestamp generated by the service. Closed-period and backdating rules
  remain undefined. Clock and UUID factories can be injected for deterministic use.

Run the tests with `uv run pytest tests/unit tests/service_layer`, then
`uv run ruff check .` and `uv run ruff format --check .`. No database is required.
