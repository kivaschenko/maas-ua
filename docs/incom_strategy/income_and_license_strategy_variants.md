# **Стратегії монетизації та захисту MAAS-UA**

**Моя основна рекомендація — не поспішати робити MAAS-UA публічним open-source проєктом під MIT.** На нинішньому етапі в тебе є можливість зберегти контроль над кодом, перевірити комерційний потенціал, залучити розробників і лише потім визначити, яку частину системи відкривати.

Для MAAS-UA я бачу чотири реалістичні моделі:

1. **Open Core** — безкоштовне відкрите ядро та платні корпоративні можливості.
2. **Комерційне ліцензування й упровадження** — закритий продукт із платною підтримкою.
3. **Грантове фінансування** — Український фонд стартапів, Brave1 та інші програми.
4. **Community Open Source** — відкритий проєкт, донати, спонсорство та оплачувані розробки.

Найбільш перспективною для тебе я вважаю комбінацію першої та другої моделей із можливістю залучення гранту.

Але спочатку є два юридичні питання, важливіші за вибір бізнес-моделі.

## **1. Що зараз означає MIT-ліцензія для твого приватного GitHub-репозиторію**

MIT — дуже ліберальна ліцензія. Вона дозволяє іншим використовувати, змінювати, поширювати й комерціалізувати код, зберігаючи належні повідомлення про авторське право та ліцензію.

Водночас **приватний репозиторій із файлом LICENSE не означає, що ти вже опублікував код для всіх**.

| Ситуація                                           | Наслідки                                                                       |
| -------------------------------------------------- | ------------------------------------------------------------------------------ |
| Репозиторій приватний, доступ маєш тільки ти       | Код не є загальнодоступним                                                     |
| Ти надав сторонньому розробнику копію коду під MIT | Він може отримати права використання відповідно до MIT                         |
| Ти зробив репозиторій публічним під MIT            | Інші можуть легально створювати власні комерційні версії                       |
| Ти згодом змінив ліцензію                          | Раніше правомірно надані MIT-права на отримані копії зазвичай не відкликаються |
| Ти залишив майбутні версії приватними              | Можеш пропонувати їх за комерційною ліцензією, якщо маєш необхідні права       |

GitHub підтверджує, що ліцензія визначає умови використання й поширення коду, а без наданої ліцензії діє стандартний захист авторського права.&#x20;

**Що зробити зараз:** перевірити фактичний `LICENSE`, copyright notice, історію доступу до репозиторію та чи не передавався код третім особам на умовах MIT. До завершення юридичної перевірки я б залишив репозиторій приватним.

- Чи було офіційне доручення розробити систему.
- Чи використовувався службовий час, обладнання або непублічні матеріали.

Ці питання не варто намагатися вирішити простим додаванням власного імені до LICENSE.

## **4. Як залучати розробників і не втратити контроль над кодом**

Я рекомендую розділити **право користування програмою, авторство внесків та право комерційного ліцензування**.

Для MAAS-UA підійшла б така структура:

**MAAS-UA — власник або уповноважений правовласник IP**

**Community repository**

Відкриті модулі, issues, pull requests, зовнішні contributors

**Commercial repository**

Закриті модулі, інтеграції, контракти, платна підтримка

Перед прийняттям зовнішніх внесків бажано мати:

- `CONTRIBUTING.md` — правила внесення змін, code review, тестування, безпека.
- `CLA` (*Contributor License Agreement*) — угоду, що надає тобі або юридичній особі достатні права на використання внеску, зокрема для комерційного ліцензування.
- `SECURITY.md` — приватний порядок повідомлення про вразливості.
- `CODEOWNERS` і захист основної гілки — без прямого запису сторонніх учасників.
- Окремі письмові договори з оплачуваними розробниками щодо майнових прав, конфіденційності та результатів робіт.

CLA не обов'язково означає передачу авторства або всіх майнових прав. Наприклад, contributor може зберігати власні права, водночас надаючи проєкту широку ліцензію для комерційного використання. Саме таку відмінність пояснює Open Source Initiative.&#x20;
